# CRM Backend API

A production-oriented **CRM RESTful API** built with **ASP.NET Core / .NET 8**, designed to manage customers, follow-ups, sales operations, status history, and business analytics.

The system provides a centralized backend for managing the complete customer lifecycle — from creating a customer and tracking follow-ups to completing a sale and analyzing business performance.

## 📌 What is this project?

This project is a **Customer Relationship Management (CRM) system** for businesses that handle customers through repeated follow-ups and sales operations.

Instead of keeping customer information and follow-up history scattered across different places, the system keeps the entire customer lifecycle in one backend.

The system allows employees to:

* Manage customers and their information
* Create and track follow-ups
* Record selling and buying operations
* Track device condition and payment type
* Track the complete status history of each follow-up
* Monitor completed sales
* Analyze conversion rates and business performance
* Identify the best-performing platforms, devices, governorates, and areas
* Track customer growth over time

---

# 👥 Users & Access Control

The system supports different levels of access depending on the user's role.

### Admin

The **Admin** has full access to the system.

Can:

* Create, update, and delete customers
* Manage follow-ups
* View customer and follow-up history
* Manage sales-related data
* Access analytics and reports
* Manage users and authentication-related operations

### Employee

The **Employee** can perform the day-to-day CRM operations required to handle customers.

Can:

* View customers
* Add customers
* Create follow-ups
* Update operational follow-up information
* Track customer interactions
* View sales and follow-up information
* Access permitted analytics

Sensitive management operations such as deleting or modifying critical customer data are restricted to the Admin.

Authorization is enforced on the API level using **ASP.NET Core Identity + JWT + Role-based Authorization**.

# 🔄 Business Flow

The main idea of the system is to follow the customer's journey through a sequence of follow-ups.

```text
Customer
   │
   ▼
Create Customer
   │
   ▼
Create Follow-up
   │
   ├── Platform
   ├── Operation Type
   ├── Device Condition
   ├── Device Type
   ├── Payment Type
   └── Notes
   │
   ▼
Follow-up Status History
   │
   ├── New Follow-up
   ├── On The Way
   ├── No Answer
   ├── Postponed
   ├── Cancelled
   └── Purchased
          │
          ▼
       Completed Sale
          │
          ▼
      Analytics
```

A customer can have **multiple follow-ups**, and every follow-up can have multiple status changes.

The system does not simply overwrite the previous status.

Instead, every status change is stored in `StatusFollowup`, creating a historical timeline for the follow-up.

For example:

```text
Follow-up #15

NewFollowup
      ↓
OnTheWay
      ↓
NoAnswer
      ↓
Postponed
      ↓
OnTheWay
      ↓
Purchased
```

This allows the system to preserve the complete history of what happened to the follow-up.

---

# 🧠 Current Status Logic

The current status of a follow-up is determined from its status history.

The system considers the latest status based on:

```text
ChangedAt DESC
        +
Id DESC
```

This means the system does **not** rely on insertion order alone.

The latest status is the status with the greatest `ChangedAt`, with `Id` used as a tie-breaker.

This logic is also used by the analytics layer when determining whether a follow-up currently represents a completed sale.

---

# 💰 What counts as a Sale?

A follow-up is considered a **completed sale** only when:

```text
Follow-up is not deleted
        AND
OperationType = Selling
        AND
Latest Status = Purchased
```

For example:

```text
Selling
   ↓
NewFollowup
   ↓
OnTheWay
   ↓
Purchased
```

→ This is a sale.

But:

```text
Selling
   ↓
Purchased
   ↓
Cancelled
```

→ This is **not considered a current completed sale**, because the latest status is `Cancelled`.

This business rule is consistently applied throughout the analytics queries.

# 🔐 Authentication & Authorization

Authentication is implemented using:

* **ASP.NET Core Identity**
* **JWT Authentication**
* **Role-based Authorization**

The authentication flow is:

```text
Login
  │
  ▼
Validate Credentials
  │
  ▼
ASP.NET Core Identity
  │
  ▼
Load User Roles
  │
  ▼
Generate JWT
  │
  ▼
Client sends JWT with requests
  │
  ▼
JWT Authentication Middleware
  │
  ▼
Authorize Endpoint
```

The JWT contains the required claims, including:

* User identifier
* Role
* Token identifier

Protected endpoints can then restrict access based on the authenticated user's role.

Example:

```http
Authorization: Bearer <JWT>
```

# 🏗️ Architecture

The backend follows **Clean Architecture**, separating business logic from infrastructure and API concerns.

```text
             ┌──────────────────────┐
             │       API            │
             │ Controllers / Auth   │
             └──────────┬───────────┘
                        │
                        ▼
             ┌──────────────────────┐
             │    Application       │
             │ CQRS / MediatR       │
             │ DTOs / Validation    │
             └──────────┬───────────┘
                        │
                        ▼
             ┌──────────────────────┐
             │       Domain         │
             │ Entities / Enums     │
             │ Business Rules       │
             └──────────────────────┘
                        ▲
                        │
             ┌──────────┴───────────┐
             │    Infrastructure    │
             │ EF Core / SQL Server │
             │ Identity / Repos     │
             └──────────────────────┘
```

### Domain

Contains the core business models and rules:

* Customers
* Follow-ups
* Status history
* Areas
* Governorates
* Users
* Enums

The Domain layer does not depend on infrastructure or API concerns.

### Application

Contains application-specific business logic:

* Commands
* Queries
* Handlers
* DTOs
* Validators
* Repository interfaces
* Mapping
* MediatR behaviors

### Infrastructure

Responsible for external implementations:

* Entity Framework Core
* SQL Server
* Repository implementations
* ASP.NET Core Identity
* JWT implementation
* Database configuration

### API

Responsible for exposing the system through HTTP:

* Controllers
* Authentication configuration
* Authorization
* Middleware
* Exception handling
* Swagger/OpenAPI
* Dependency Injection configuration

# 🔀 CQRS & MediatR

The application follows the **CQRS** pattern.

Operations are separated into:

### Commands

Used when changing data.

```text
CreateCustomerCommand
UpdateCustomerCommand
CreateFollowupCommand
UpdateFollowupCommand
...
```

### Queries

Used when retrieving data.

```text
GetCustomerQuery
GetSalesAnalyticsQuery
GetPlatformAnalyticsQuery
GetTopDevicesQuery
...
```

Each request is handled by its corresponding MediatR handler.

```text
HTTP Request
     ↓
Controller
     ↓
MediatR
     ↓
Command / Query
     ↓
Handler
     ↓
Repository
     ↓
EF Core
     ↓
SQL Server
```

This keeps controllers thin and moves application logic into dedicated handlers.

# 🗄️ Data Access

The project uses:

* **Entity Framework Core**
* **SQL Server**
* **LINQ**
* **Repository Pattern**
* **Async database operations**
* **EF Core Migrations**

Database queries are kept server-side whenever possible.

For analytics, filtering, grouping, ordering, and aggregation are translated into SQL and executed by SQL Server rather than loading unnecessary records into memory.

Example flow:

```text
LINQ
  ↓
EF Core
  ↓
SQL Translation
  ↓
SQL Server
  ↓
Aggregated Result
```

---

# 📋 Validation & Error Handling

Input validation is implemented using **FluentValidation**.

The application uses a MediatR validation behavior so requests can be validated before reaching their handlers.

```text
Request
   ↓
Validation Behavior
   ↓
Valid?
 ┌─┴─────────┐
No           Yes
↓             ↓
Error       Handler
Response       ↓
             Repository
```

Global exception handling is implemented through custom middleware, providing consistent API error responses instead of handling exceptions individually inside every controller.

# 🚀 Getting Started

### 1. Clone the repository

```bash
git clone <repository-url>
cd CRM
```

### 2. Configure the database

Update the SQL Server connection string in:

```text
appsettings.json
```

### 3. Apply migrations

```bash
dotnet ef database update
```

### 4. Run the API

```bash
dotnet run
```

### 5. Open Swagger

```text
/swagger
```
